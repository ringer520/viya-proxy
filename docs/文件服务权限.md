# 文件服务权限范围

Viya 有两个文件入口，权限模型完全不同。多数“文件打不开”的疑问来自把两者混在一起，所以先分清它们。

| | 服务器文件服务 | 站点文件管理 |
| --- | --- | --- |
| 入口 | 左侧「文件服务」页（默认隐藏，需在设置里打开） | 站点卡片里的「管理站点文件」 |
| 接口 | `/api/v1/files/*` | `/api/v1/proxy-hosts/{id}/files/*` |
| 根目录 | `VIYA_FILES_ROOT`，默认 `/` | 托管目录 `/var/lib/viya/sites/<域名>` |
| 受只读开关约束 | **是**，`VIYA_FILES_READONLY=1` 时所有写操作直接 403 | **否**，始终可读写 |
| 适用站点类型 | 全部 | 只有 `static` 与 `files` |

本文只讨论第一个。第二个受应用层硬限制：写入必须落在托管目录内，`root_path` 指向外部路径（如 `/var/www/site`）时上传会返回 400「该站点目录由面板外部管理」，加 ACL 也绕不过。

## 默认能看到什么

文件服务以 `User=viya` 运行，同时受 systemd 的三层限制。任何一层都会挡住访问：

| 限制 | 默认值 | 影响 |
| --- | --- | --- |
| 运行用户 | `User=viya` | 非该用户拥有的 `700` 目录全部拒绝，例如 `/root`、Docker 的 `/var/lib/docker` |
| `ProtectHome=true` | 开启 | `/home`、`/root`、`/run/user` 被空 tmpfs **遮蔽**，与文件权限无关，列目录也返回空 |
| `ProtectSystem=strict` | 开启 | 整个文件系统只读挂载，只有 `ReadWritePaths` 里的路径例外 |

在一台 Debian 12 上，默认配置的实测结果：

```
可读  /etc（211 项，但 /etc/shadow、/etc/ssl/private 被权限拒绝）
可读  /opt /var/log /usr/local
空    /home /root（被 ProtectHome 遮蔽，列目录为空）
禁止  任何写操作
```

所以它的定位是「快速查看」，不是「全盘管理」。需要完整文件管理时，用 SFTP / VS Code Remote / WinSCP 连 SSH 体验更好。

## 扩大只读范围

两处改动，都在 `/etc` 下，不动代码。

### 1. 解除家目录遮蔽

主 unit 里保持 `ProtectHome=true`，定制写进 drop-in，这样升级 Viya 覆盖 unit 时不会丢：

```bash
sudo install -d -m 0755 /etc/systemd/system/viya.service.d
sudo tee /etc/systemd/system/viya.service.d/50-files-visibility.conf >/dev/null <<'CONF'
# 文件服务可见范围（运维定制，升级 Viya 不会覆盖本文件）。
# 主 unit 默认 ProtectHome=true，会把 /home、/root 整段遮蔽；
# 改为 read-only 只解除遮蔽，是否可读仍取决于 unix 权限，
# 写入依旧被 ProtectSystem=strict 拦住。
[Service]
ProtectHome=read-only
CONF
sudo systemctl daemon-reload
sudo systemctl restart viya
```

`read-only` 只解除遮蔽，不改权限。能不能读仍由 uid 与 ACL 决定。

反过来也有总闸：`VIYA_FILES_ROOT` 决定文件服务的根。设成 `/srv` 就只看 `/srv` 并且出不去，比逐目录授权更省事，也更容易解释给其他人听。

### 2. 给 viya 用户授只读 ACL

```bash
# rX：目录加执行位才能遍历，文件只加读位
sudo setfacl -R -m u:viya:rX /home/ryan
```

敏感子目录应当单独拒绝，而不是靠“没人会点开”：

```bash
for d in /home/ryan/.ssh /home/ryan/.gnupg; do
  [ -d "$d" ] && sudo setfacl -R -m u:viya:--- "$d"
done
```

验证：

```bash
sudo -u viya ls /home/ryan | wc -l          # 条目数
sudo -u viya ls /home/ryan/.ssh             # 应为 Permission denied
sudo -u viya touch /home/ryan/__probe       # 应为 Permission denied
```

同一台 Debian 12 上的实测（`/home/ryan` 有 8 个条目）：目录可读、`.ssh` 若存在则被拒、写入被拒，`/root` 依旧拒绝。

`/root` 不建议开。它存放 SSH 私钥与各类密钥，为了“能在面板里看到”而放权不划算。确实需要时单独 `setfacl -m u:viya:rX /root`，并清楚这意味着面板被攻破即可读走主机凭据。

## 要不要开放写入

`VIYA_FILES_READONLY=0` 只在**应用层**解除写保护，系统层仍会挡住：写入还要落在 `ReadWritePaths` 内。

```ini
# /etc/systemd/system/viya.service.d/60-files-write.conf
[Service]
Environment=VIYA_FILES_READONLY=0
ReadWritePaths=/var/lib/viya /opt/viya/bin /srv/data
```

只给专用数据目录，不要给 `/`。以 root 运行 + 全盘读写的后果是单向的：

- 可写 `~/.ssh/authorized_keys` → 直接获得 SSH 登录
- 可写 `/etc/cron.d/` → 定时回连
- 可改 `/etc/ssh/sshd_config`、`/etc/fstab` → 自己都进不去
- 可读 `/etc/viya/secrets/master.key` → 解密所有已存凭据

面板一旦被攻破，破坏范围从“改反代配置”变成“整机接管”，而且回退时无法确认是否已被埋东西。文件管理器没有回收站，误删 `/etc` 下某个目录也是两次点击的事。

需要全盘读写时，更省事的做法是用独立容器把范围圈住，Viya 保持最小权限：

```bash
docker run -d --name files \
  -v /opt:/srv/opt -v /etc:/srv/etc -v /var/log:/srv/logs \
  -p 8182:80 filebrowser/filebrowser
```

root 只存在于容器内，且只能碰显式挂载的三个目录，出事直接删容器重建。

## 访问被拒时的错误语义

后端按原因返回不同状态码，可以据此判断是权限问题还是路径问题：

| 情况 | 状态码 |
| --- | --- |
| 只读模式下发起写操作 | 403（进入处理前拦截，不会看到 `EROFS`） |
| 文件系统 `EACCES` / `EROFS` | 403 |
| 路径不存在 `ENOENT` | 404 |
| 路径含 `..` 或指向根外 | 400 |

路径安全有三道防线：拒绝 `..`、拒绝符号链接、用 `os.OpenRoot` 把文件操作限制在根内，因此扩大可见范围不会同时扩大可越界范围。

## 换机器要重做什么

drop-in 与 ACL 都是手工配置，不在安装包里。新机器需要重做：

1. 写 `/etc/systemd/system/viya.service.d/50-files-visibility.conf`
2. `setfacl -R -m u:viya:rX <目录>`，再对敏感子目录 `---`
3. `systemctl daemon-reload && systemctl restart viya`

自检：

```bash
systemctl show viya -p ProtectHome --value   # read-only
sudo -u viya ls /home/ryan | wc -l           # 大于 0
sudo -u viya touch /home/ryan/__probe        # Permission denied
```

如果换成了别的运行账号，ACL 里的 `u:viya` 要跟着改。
