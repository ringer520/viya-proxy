# Viya v0.6.7

修复 v0.6.6 引入的一个升级回归：**从旧版本升级时，轮转日志会被从头重采，导致流量统计重复计数**。如果在 v0.6.6 上看到请求数突然翻倍、错误率被拉高，就是这个原因。

## 问题

v0.6.6 把日志的内容指纹从 `sha256(首行)` 改成 `sha256(日志家族 + 首行)`，用 `http` / `l4` 前缀区分两个日志文件，避免它们因为共同的启动首行而共用一个 generation。

但旧版本写入 `traffic_cursors` 的 generation **没有家族前缀**。新版本查不到这些记录，就把早已采完的轮转文件当成新文件，从第 0 字节重读了一遍。

实测一台机器上，11-05 的 41 MB access 轮转文件和 57 MB l4 轮转文件被重采，`traffic_hours` 的累计请求从 67,194 涨到 126,351（多算约 5.9 万），Web 错误率被历史高错误数据从 35% 拉到 40%。趋势图也因此只剩一个大尖峰。

## 修复

- **兼容旧游标**：`inheritedTrafficOffset()` 先用新 generation 查，查不到再回退到 `legacyTrafficGeneration()`（即旧版的 `sha256(首行)`）。从任何旧版本升级都不会再重放已消费的日志。
- **按文件类型过滤**：`access*.log*` 只接受 HTTP 访问行，`l4*.log*` 只接受 `layer4` 连接行。历史文件里两种行都有（旧日志配置把每条日志写进了两个文件），这条规则保证**无论重采多少次都不会重复计数**，也不再依赖 Caddy 配置是否已经生效。
- **重建友好**：`seedTrafficCursors()` 只在 `traffic_files` 已有采集记录时预写偏移；表被清空后（重建场景）会从日志开头读，而不是从末尾跳过。

## 数据修复

v0.6.6 到 v0.6.7 之间被多算的数据不会自行消失。因为日志文件完整保留（`access.log` / `l4-access.log` 与四个轮转文件），可以按下面的步骤重建，得到按新口径统计的准确数据：

1. 停止 Viya，备份 `/var/lib/viya/viya.db`；
2. 清空 `traffic_hours`、`layer4_traffic_hours`、`site_access_events`、`traffic_cursors`、`traffic_files` 五张表（保留 `panel_settings` 与站点配置）；
3. 启动 Viya，采集会按文件类型过滤，从日志开头重建 11-05 以来的所有小时桶；
4. 用面板核对累计请求数与日志规模是否匹配（这台机器重建后应在 6–7 万量级，而不是 12 万）。

如果不想动历史数据，也可以只升级不重建：从 v0.6.7 起新数据准确，历史里多出的约 5.9 万条会一直留在累计值中。

## 升级注意

- 无 schema 变更，`traffic_files.generation` 列在 v0.6.6 已补，v0.6.7 不再动表结构。
- 从 v0.6.6 升级：不会再重采；已多算的按上面重建。
- 从 v0.6.5 及更早升级：直接到 v0.6.7，不会经过 v0.6.6 的重采问题。
- 升级前建议照旧备份 `/var/lib/viya`（`viya.db` 与 `master.key`）。

## 验证

`go vet ./...`、`go test ./...`、`golangci-lint run`、`pnpm typecheck / build / lint / vitest`、`check_i18n.py`、`check_release_version.py v0.6.7`、Python 脚本测试与 shell 语法全部通过。新增两个回归单测：旧版 generation 记录不重放、跨类型日志行不计入。
